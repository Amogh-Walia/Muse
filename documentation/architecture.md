# Architecture

Muse is a small Python web app with no web framework: `http.server` from the standard library, SQLite, and ffprobe/ffmpeg. The only third-party package is [mutagen](https://mutagen.readthedocs.io/), for writing tags.

## Code layout

| Path | What it does |
|---|---|
| `config.py` | Reads settings from the environment and `.env`. Every other module takes its settings from here. |
| `app.py` | Web server: JSON API, cover images, the single-page UI, and one-at-a-time background jobs with progress. |
| `scan.py` | Probes audio files with ffprobe and brings the catalog in line with the disk. It's also a CLI. |
| `static/index.html` | The whole UI: Albums, Tracks, Ingest and Operations tabs, plus the Cleanup, MusicBrainz, clash and Appearance dialogs. |
| `static/style.css` | The style sheet. Every colour that carries meaning comes from five tokens (`--accent`, `--link`, `--ok`, `--warn`, `--danger`); tints are mixed from them, so changing a token restyles everything that uses it. |
| `/theme.css` | Generated by `app.py` from `config.colors()`: the five tokens for light and dark mode, from `.env` or the defaults in `config.py`. The Appearance menu writes them to `.env`. |
| `crud/` | **All** database access. Nothing else runs SQL. |
| `cleanup/` | Regex rules for tags and file names, the planner, apply/undo with journals, clash comparison, ingestion status. It's also a CLI (`python -m cleanup`). |
| `musicbrainz/` | Rate-limited MusicBrainz client, release matching, proposals, and alignment of mixed editions. |
| `artwork/` | Cover candidates (folder, embedded, Cover Art Archive, iTunes, uploads), image checks and resizing, and embedding. |
| `lyrics/` | Where a song's lyrics are (`.lrc`, `.txt`, embedded) and what kind, the LRCLIB client, saving lyrics files, orphaned `.lrc` files, and parsing synced lyrics for the player. |
| `transfer/` | Import (a folder from anywhere on this machine into the inbox, journaled for undo) and export (album folders copied out, keeping the library's structure), plus the folder picker's listing. |
| `navidrome/` | Subsonic API client (token auth, server side only), starting Navidrome if it's down, rescans, and linking songs to Navidrome ids. |

## Database

SQLite in WAL mode, so the web app keeps reading while a job writes. It's created on first start, and tables and columns added in later versions are migrated automatically (`crud/db.py`).

| Table | Contents |
|---|---|
| `tracks` | One row per audio file. Common fields (title, artist, album, track/disc, year, genre), audio properties, MusicBrainz links, and ingestion status (`clean_path`, `processed`). |
| `tags` | Every raw tag exactly as stored in the file, including lyrics, ReplayGain and MusicBrainz IDs. |
| `meta` | The library folder and the time of the last scan. |
| `releases` | MusicBrainz releases songs are linked to: tracklist, full details, completeness. |
| `missing_tracks` | Songs on a release that aren't in the library: name and position only. |
| `mb_proposals` | MusicBrainz matches waiting for review. |
| `art_candidates`, `artwork` | Cover candidates per album, and what was embedded. |

Paths in the database are relative to the library folder, so a library can move: update `MUSE_LIBRARY` and restart.

## Keeping files and catalog in step

Every operation that changes files (cleanup, MusicBrainz apply, artwork, undo) follows the same pattern:

1. Change one file: write tags with mutagen or move it.
2. Record what was there before in a journal entry.
3. Re-read that file into the catalog (`scan.refresh`) and commit.

A run that stops halfway leaves the catalog matching the disk, and its journal covers exactly what was done. A moved song keeps its database ID. After each run, `crud.tracks.verify` compares the catalog with the disk, and the UI reports any difference.

Tag writing is careful about the files it touches (`cleanup/tags.py`):
- **Audio data is never rewritten.** Existing padding is reused, so files usually keep their size.
- **FLAC/Ogg keys keep their spelling.**
- **MP3s keep their ID3 version,** so v2.3 frames survive.

## Journals and undo

Journals are JSON files in `MUSE_JOURNAL_DIR`, named with a microsecond timestamp so runs can't collide. **Undo** reverses the newest journal of the current library: moves back first, then tags and pictures. Pictures replaced by the artwork operation are kept in a backup folder beside the journal. Duplicates discarded in a name clash go to `.muse-trash/` inside the library and come back on undo.

**Retention** (`cleanup/retention.py`): a change stays undoable for `MUSE_UNDO_DAYS` (default 30). After that, its journal expires together with its picture backups and its `.muse-trash/<stamp>/` folder, whose duplicates are then deleted for good. Only the oldest changes expire, so Undo keeps working. Journals already undone, backup folders without a journal, cached covers nothing refers to, and candidates/proposals for albums that no longer exist are removed straight away. Pruning runs at startup and after every job; `python -m cleanup --history` shows what's kept and when it expires, and the Operations tab shows the same.

## Jobs

Scans, cleanups, MusicBrainz runs and artwork runs change files, so only one runs at a time (`JOB_LOCK` in `app.py`). Each reports progress to `/api/progress`, which drives the progress bars. After every job, processed flags, album completeness and mixed-edition alignment proposals are recomputed. Then, in a background thread, Navidrome is asked to rescan and every song is re-linked to its Navidrome id. Only one such pass runs at a time; a request mid-pass triggers one more.

Jobs run on the server, so they carry on whatever the page does: switching tabs, reloading, or closing it. The page keeps track of them through one shared poller in `index.html`:
- **Polling:** the poller asks `/api/progress` every half second while a job runs, and every few seconds otherwise, so it notices jobs started from another tab or device.
- **Display:** it draws every progress bar (each `.progress` box lists the jobs it shows in `data-ops`) and the job indicator in the header (with Stop), and keeps the job's pane disabled.
- **Running a job:** `runJob(pane, path, body)` is the single way a pane starts one. It turns the pane's buttons off, posts, reloads the pane, then sums up the result from `JOB_TEXT`.
- **Coming back:** a pane opened while a job it runs is in progress follows that job (`attachJob`). `/api/progress` also returns the last finished job (`last`), so a page that comes back says how it ended: a stop or failure always, a success if it was recent. Jobs are numbered, so each outcome is shown once.

Lookups (Scrape Details, artwork and lyrics searches) can stop between items. They stop when Stop is pressed (`POST /api/jobs/stop`), or by themselves when no page has asked for progress for `MUSE_STOP_UNWATCHED` seconds: every open Muse page polls, so that means nobody has Muse open. Each item's result is saved as soon as it's found, so nothing is lost. The stopped result carries `continue`: the same request, with the finished items added to `skip`. Jobs that change files (Clean up, Apply, Merge, Undo) never stop halfway.

## Playback

`/stream/<track id>` plays a song. A song linked to Navidrome is proxied from Navidrome's `/rest/stream`: the file as-is with Range requests passed through for seeking, or transcoded to MP3 320 for formats browsers can't play (ALAC). A song without a link, or with no Navidrome set up, is served straight from disk with Range support, if the browser can play its format.

Songs are linked by real path first: Navidrome reports it when `Subsonic.DefaultReportRealPath` is on, and a Docker-style mount prefix is fine. Otherwise by MusicBrainz recording id, otherwise by album, disc, track and title.

POST endpoints only accept `Content-Type: application/json`. That forces a CORS preflight, so other websites open in your browser can't trigger them.
